How the backup works

The backup is a shell script run by cron. It creates a dated, compressed archive, records a SHA-256 checksum so corruption can be detected, and deletes archives older than 14 days.

#!/usr/bin/env bash
# Nightly backup of /srv/data on fs-01. Documented in RB-BKP-002.
set -euo pipefail

STAMP="$(date +%F)"                  # e.g. 2026-10-28
DEST="/mnt/backups/fs-01"            # NFS share on bkp-01
ARCHIVE="$DEST/fs-01-data-$STAMP.tar.gz"
LOG="/var/log/backup/nightly-$STAMP.log"

{
  echo "[$(date '+%F %T')] Backup started"
  tar -czf "$ARCHIVE" -C /srv data
  sha256sum "$ARCHIVE" > "$ARCHIVE.sha256"
  find "$DEST" -name 'fs-01-data-*' -mtime +14 -delete
  echo "[$(date '+%F %T')] Backup finished ($(du -h "$ARCHIVE" | cut -f1))"
} >> "$LOG" 2>&1
# min hour day month weekday  user  command
30    1    *   *     *        root  /usr/local/sbin/nightly-backup.sh

Daily check (every morning)

  1. Confirm last night's backup finished. 
    tail -n 2 /var/log/backup/nightly-$(date +%F).log
    Expected: a line ending in Backup finished (…G).
  2. Check that the archive exists and its size looks normal (about 60–70 GB compressed). 
    ls -lh /mnt/backups/fs-01/ | tail -n 4
  3. Verify the checksum. 
    sha256sum -c /mnt/backups/fs-01/fs-01-data-$(date +%F).tar.gz.sha256
    Expected: /mnt/backups/fs-01/fs-01-data-2026-10-28.tar.gz: OK
  4. Record the resultin the daily operations log (ticket queue “Backups”).

Restore a single file or folder

Before you start

Confirm the request comes from someone who is allowed to access that data. Restoring a file for someone without access would be a privacy violation (see Ethics: privacy).

  1. Find the archive from before the file was lost. 
    ls /mnt/backups/fs-01/
  2. Confirm the file is in the archive. 
    tar -tzf /mnt/backups/fs-01/fs-01-data-2026-10-27.tar.gz | grep 'finance/budget-2026.xlsx'
  3. Extract it to a temporary folder. 
    mkdir -p /tmp/restore
tar -xzf /mnt/backups/fs-01/fs-01-data-2026-10-27.tar.gz -C /tmp/restore data/finance/budget-2026.xlsx
  4. Copy it back under a new name so nothing newer is overwritten. 
    sudo cp -p /tmp/restore/data/finance/budget-2026.xlsx \
  /srv/data/finance/budget-2026.restored-2026-10-27.xlsx
rm -rf /tmp/restore
  5. Tell the userwhere the restored file is, and close the ticket.

Warning

Never extract an archive directly over /srv/data. It overwrites every newer file in the share.

Full restore (disaster recovery)

Use this only when fs-01 or its data is lost. Target: service restored within the 4-hour RTO.

  1. Declare an incidentand notify the IT Manager. Open an incident record.
  2. Build or repair the serverusing the fs-01 build document, with the same hostname and IP.
  3. Mount the backup share and verify the latest archive. 
    sudo mount -a
sha256sum -c /mnt/backups/fs-01/fs-01-data-2026-10-28.tar.gz.sha256
    If bkp-01 is also lost, retrieve the archive from off-site storage (RB-BKP-003).
  4. Restore the data. 
    sudo tar -xzf /mnt/backups/fs-01/fs-01-data-2026-10-28.tar.gz -C /srv
  5. Start the file sharing service and test from a client PC. 
    sudo systemctl restart smbd
systemctl is-active smbd
  6. Notify usersthat service is back and that changes made after the backup time may need to be redone. Then complete the incident report.

Troubleshooting

SymptomLikely causeAction
No log file for todayCron did not run, or fs-01 was down at 01:30Check systemctl status cron and grep CRON /var/log/syslog. Run the script manually with sudo.
No space left on device in the logThe backup volume on bkp-01 is fullCheck df -h /mnt/backups. Confirm old archives were deleted. Escalate to L2.
computed checksum did NOT matchThe archive is corruptedDo not rely on that archive. Re-run the backup and open an incident.
Stale file handle or /mnt/backups is emptyThe NFS mount to bkp-01 droppedCheck with findmnt /mnt/backups, remount with sudo mount -a, and check that bkp-01 is up.
