Documentation Standards

Documentation standards are the agreed rules for what we document, how we write it, and how we keep it accurate. They make documents from different people look, read and behave the same way.

What is system documentation?

System documentation is the written record of how an organization's IT environment is built, configured, operated and supported. It covers the hardware and software you run, how they connect, the procedures for working on them, and the history of what has changed.

A useful test is the “hit by a bus” test (sometimes called the lottery test): if the only person who knows a system suddenly left, could someone else keep it running using only the documentation? If not, the documentation is incomplete.

Note

Documentation is written for a specific reader. A runbook is for the on-call admin at 3 a.m. A policy is for every employee. A network diagram is for engineers and auditors. Decide who will read it before you start writing.

Qualities of good documentation

Whatever its type, good documentation has the same qualities. A simple way to remember them is the seven Cs:

Recognized standards and frameworks

Organizations don't have to invent documentation rules from scratch. These published standards and frameworks are widely used as a reference:

ISO 9001 (clause 7.5)“Documented information” must be identified, reviewed, approved, version-controlled, protected and kept available. This is the basis of document control.

Writing style rules

A style guide makes documents written by different people read as if one person wrote them. These are common rules used by IT teams.

Writing procedures

  • Number the steps and put one action in each step.
  • Start each step with a verb in the imperative mood: “Restart the service”, not “The service should be restarted”.
  • Show the expected result after important steps so the reader knows it worked.
  • List prerequisites (access, tools, approvals) before step 1.
  • Always include verification and rollback steps.
  • Put commands in code blocks without the shell prompt ($ or #) so they can be copied and pasted safely.

Language and formatting

  • Use active voice and plain English. Short sentences are better.
  • Define acronyms the first time they appear, e.g. Standard Operating Procedure (SOP).
  • Write dates in ISO 8601 format, YYYY-MM-DD (e.g. 2026-10-28), which no reader can misread.
  • Use clear placeholders for values the reader replaces, e.g. <username>, and explain them.
  • In public examples use reserved names and addresses, such as example.com (RFC 2606) and 192.0.2.0/24 (RFC 5737), so you never expose or target a real system.
  • Give every screenshot or diagram a caption and alt text, and never rely on an image alone for a critical step.

Example: a poor step vs. a good step

Poor

“Then you should probably restart the web server and check if it's working again.”

  • Vague (“probably”, “check”)
  • No command and no expected result

Good

  1. Restart the web server: sudo systemctl restart nginx
  2. Confirm it is running: systemctl status nginx
    Expected: Active: active (running)

Version numbers

  • 0.1 – 0.9: drafts, not yet approved for use.
  • 1.0: the first approved, published version.
  • 1.1, 1.2 …: minor changes such as corrections or clarifications.
  • 2.0: a major change, such as a new process, which needs re-approval.

Document status

Draft In Review Approved Superseded

The status tells readers whether they can rely on a document. Only Approved documents should be followed in production. Superseded versions are archived, not deleted, because auditors may need them.

The documentation lifecycle

When to review a document

  • On a fixed schedule, at least once a year (the “Next review” date).
  • Whenever the system it describes changes. Updating the docs should be part of every change request.
  • After an incident shows that the documentation was wrong or missing.
  • When the document owner leaves or changes role. Assign a new owner immediately.

Documentation and security

Documentation describes how to access and control your systems, so it is sensitive in its own right.

Never put secrets in documentation

Passwords, private keys, API tokens and recovery codes belong in a password manager or secrets vault. The document should say where the credential is stored (“see vault entry fs-01 / root”), never what it is.

  • Label every document with a classification (Public, Internal, Confidential, Restricted).
  • Restrict who can edit controlled documents, and keep an edit history.
  • Keep an offline copy of critical runbooks. If the wiki server is down, you still need the recovery steps.

Common mistakes

  • “Doc rot”: written once and never updated, so it is now wrong.
  • Assumed knowledge: “just fix the config on the usual box”.
  • No owner, so nobody feels responsible for keeping it accurate.
  • Walls of text with no headings, steps or tables.
  • Screenshots only, which can't be searched or copied and go out of date quickly.
  • Missing dates and versions, so readers can't tell if it is still valid.
